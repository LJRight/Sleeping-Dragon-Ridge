# 용이 잠든 능선 · AI 협업 개발 기록

2026년 11월 13일부터 24일까지 Unity로 모바일 액션 RPG를 만들었습니다. 저는 게임을 기획하고 프로그래밍하며 Unity 에디터와 휴대폰에서 조작감·화면·소리를 판단했습니다. AI에는 설계 대안 조사, 코드와 제작 도구 구현, 아트·사운드 시안 제작, 재현 가능한 테스트 작성을 맡겼습니다. 처음에는 싱글플레이 중심이었고, 전용 서버와 최대 4인 파티 보스전을 포함하기로 하면서 역할과 승인 범위를 문서에 갱신했습니다. [협업 규칙과 결정 기록](../AGENTS.md) · [게임 기획](PROJECT_PLAN.md)

아래는 분기 대화를 포함한 프로젝트 대화 30개를 주제별로 정리한 기록입니다. 대화에서 나온 아이디어가 실제로 어디까지 반영됐는지 확인할 수 있도록 현재 코드와 당시 남긴 측정 자료를 연결했습니다.

## 1. “클립은 내가 배치할게. 코드만 연결해줘”

직접 플레이해 보니 일반 공격을 한 뒤 이동과 스킬이 너무 늦게 풀렸습니다. 저는 공격 판정이 시작되는 프레임, 마지막으로 맞힐 수 있는 프레임, 다음 조작이 가능한 프레임을 애니메이션에서 직접 옮기고 싶었습니다. 처음에는 클라이언트가 해당 프레임마다 서버에 RPC를 보내는 방법을 물었습니다. 논의 끝에 **클립은 타이밍의 기준으로, 서버는 타격의 결정권자로** 두었습니다. AI가 연결한 코드는 서버가 세 이벤트의 시간을 읽고 공격 시작 이후의 경과 시간으로 판정합니다. 마지막 프레임까지 유효하며, 한 프레임짜리 구간이 서버 업데이트 사이에 지나가는 경우도 처리합니다. [서버의 공격 구간 계산](../NetmarbleNeo/Assets/Scripts/Network/PlayerCombat.AttackWindows.cs)

발소리에는 다른 결정을 내렸습니다. 다른 플레이어의 복제 캐릭터도 내 기기에서 걷기 애니메이션을 재생한다는 점을 이용했습니다. 발이 닿는 이벤트에서 각 클라이언트가 열 개의 소리 중 하나를 재생하면 주변 캐릭터의 발걸음도 들립니다. 같은 애니메이션 이벤트라도 게임의 승패를 바꾸는 타격과 청각적 표현에는 서로 다른 구현을 선택했습니다. [발소리 구현](../NetmarbleNeo/Assets/Scripts/Network/PlayerFootsteps.cs)

보스 방어 모션에서는 AI가 저장된 이벤트를 하나만 찾았다고 답했습니다. 제가 에디터에서 본 86프레임의 두 번째 이벤트를 짚고, 반사 피해의 기준도 보스를 때린 플레이어 본인의 최대 체력으로 정했습니다. 구현된 규칙은 방어 자세 내내 보스가 피해를 무시하고, 30프레임에 반사를 열어 86프레임에 닫는 것입니다. [방어 자세의 규칙](BOSS_PROTOTYPE.md) · [반사 판정 코드](../NetmarbleNeo/Assets/Scripts/Network/BossCombat.cs)

## 2. UI 결과물을 에디터에서 직접 고칠 수 있게 하기

런타임에 배치하던 UI는 버튼 하나를 옮길 때도 코드 수정이 필요했습니다. 저는 “프리팹을 편집해 저장한 위치와 크기가 플레이 모드에서도 그대로 보일 것”을 완료 조건으로 정했습니다. AI가 화면과 반복 항목을 프리팹에 연결했고, 당시 검증에서는 Unity에 프리팹 28개를 임포트한 뒤 프로젝트 복사본에서 14개 요소의 Rect Transform을 바꿔 플레이 모드 값과 비교했습니다. 이후 iPhone 15 가로 화면에서는 배경을 끝까지 채우고 조작 버튼은 안전 영역 안에 배치하기로 했습니다. [프리팹별 편집 위치와 검증 결과](UI_PREFABS.md) · [iPhone 15 비율의 퀘스트 화면](verification/ui-prefabs/iphone15-journal.jpg)

기능이 맞아도 화면이나 소리가 의도와 다르면 다시 요청했습니다. 공격 버튼을 투명하게 해 달라는 요청에서 기존 그림의 디자인까지 바뀌자, 제가 유지할 원본 두 장을 지정하고 배경만 제거하도록 범위를 좁혔습니다. 강화에서는 장착 중인 장비의 능력치가 먼저 갱신돼 결과를 미리 알 수 있었습니다. 이때는 결과음이 시작되는 순간에 능력치와 결과를 함께 공개하도록 기준을 정했습니다. [공격 버튼 원본](<../NetmarbleNeo/Assets/Art/Expedition UI/attack_basic.png>) · [강화 결과 표시 코드](../NetmarbleNeo/Assets/Scripts/UI/Expedition/ExpeditionUI.cs)

## 3. 플레이어 간 교환에서 실패할 조건부터 정하기

마을에서 사냥 장비·강화 재료·골드를 교환하는 기능을 요청하면서, 저는 양쪽 플레이어가 같은 제안을 확정해야 하고 DB의 원자성과 경쟁 조건을 검증해야 한다고 지정했습니다. AI는 SQLite 쓰기 트랜잭션 안에서 양측의 데이터 버전·소유권·잔액을 다시 검사하고, 자산 이동과 거래 영수증을 함께 저장하도록 구현했습니다. [교환 처리 코드](../localServer/trading.py)

테스트에는 두 구매자가 같은 재산을 요구하는 상황, 같은 거래가 동시에 여섯 번 전송되는 상황, 자산을 옮긴 뒤 영수증 저장에 실패하는 상황이 포함됐습니다. 마지막 경우에는 양쪽 자산이 복구되고 같은 거래 ID로 재시도할 수 있어야 합니다. **11월 24일 기록에서 백엔드 테스트 40개가 통과했고, 그중 동시 요청·실패 시나리오 7개를 각 25회 반복한 175회도 통과했습니다.** [재현 가능한 테스트](../localServer/test_trading.py) · [실행 결과](../localServer/README.md#장비-판매와-플레이어-교환)

## 4. 반복해서 바꿀 값은 제작 도구로 옮기기

사냥 보상이 짜게 느껴져 몬스터와 보스의 전투 수치·처치 보상·일반 공격과 스킬 배율을 표에서 직접 조절할 수 있게 요청했습니다. 이후 제가 데이터를 손보고 전체 밸런스 검토를 다시 맡겼습니다. 자동 사냥에서도 “탐지 범위 15m”, “수동 공격 시 가까운 적이 있으면 타격 거리까지 접근하고, 없으면 제자리에서 시전”처럼 플레이 중 원하는 행동으로 기준을 정했습니다. [몬스터 밸런스 데이터](../NetmarbleNeo/Assets/Resources/MonsterBalanceCatalog.asset) · [플레이어 공격 배율](../NetmarbleNeo/Assets/Resources/PlayerAttackBalance.asset) · [밸런스 편집 창](../NetmarbleNeo/Assets/Editor/MonsterBalanceWindow.cs)

음악 작업에서는 마을·필드·보스 세 곡을 들어보고 선율이 비슷하다고 피드백했습니다. 세 곡 중 보스 곡을 골라 속도와 리듬을 바꾸고 드롭을 강조하도록 요청했습니다. 당시 제작 기록에는 112 BPM에서 160 BPM으로 바꾼 편곡과 두 드롭의 위치가 남아 있습니다. 게임에 사용할 후보를 만든 다음 제가 무엇을 남기고 어디를 다시 만들지 결정한 사례입니다. [음악 제작 기록](PROJECT_PLAN.md) · [보스 곡 제작 코드](../ArtSource/AreaMusic/boss.py)

## 5. 테스트 결과에 실행 조건과 한계를 함께 남기기

로그인 실패를 조사하면서 한 대의 에디터로 게임 동작을 확인하는 상황과, 휴대폰에서 외부 서버에 접속하는 상황을 나눴습니다. 에디터에서는 제가 `Server And Client`의 재생 버튼 한 번으로 두 서버를 시작하고 기존 게스트 진행도를 이어가도록 요청했습니다. 당시 검증에서는 첫 실행에서 37골드였던 게스트가 튜토리얼 후 47골드와 검을 얻었고, 재시작 뒤에도 같은 진행도가 복원됐습니다. 별도로 휴대폰과 Windows 서버 용도에는 접속 호스트, 로그인 TCP·게임 UDP 포트, 실행 절차를 정리했습니다. [두 번의 에디터 실행 기록](BOOTSTRAP_TEST.md) · [다른 PC에서 서버 실행하기](../README.md#내-windows-pc와-휴대폰으로-테스트)

퀘스트 자동 진행은 빈 DB의 새 게스트가 마을에서 보스 관문까지 가는 경로를 실제 시간으로 측정했습니다. 당시 버전의 결과는 **18분 52초**였습니다. 이후 첫 강화 의뢰를 추가한 버전의 재측정은 도중에 클라이언트 연결이 끊겼습니다. 그래서 이전 기록이 어느 버전의 어느 구간을 설명하는지 함께 남겼습니다. 제출 직전에는 여러 연출 변경의 실행 검증을 제가 명시적으로 생략했고, 거래처럼 진행 데이터가 손실될 수 있는 기능에는 반복 검증을 요청했습니다. [진행 구간별 측정과 중단 기록](QUEST_STORY_FLOW.md) · [승인한 검증 범위](../AGENTS.md)
