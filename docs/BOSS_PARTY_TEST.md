# 보스 파티·의뢰 보상 검증

2026-11-20 · Unity 6000.3.10f1 · macOS Apple Silicon · Python·SQLite 진행 서버

## 플레이 방법

1. 경비대장에게 ‘능선의 위협’을 보고해 관문을 열고 보스 의뢰 ‘능선의 주인’을 수락한다. 보스 의뢰 보고를 마친 기사도 다른 파티의 도전을 도울 수 있다.
2. 파티로 도전하려면 필드에 보이는 다른 기사를 눌러 초대한다. 최대 네 명이다. 첫 입장은 능선 관문에서, 첫 입장을 기록한 뒤에는 야영지에서도 가능하다. 참가자가 같은 입장 지점에 모이면 파티장이 입장을 요청하고 나머지 파티원이 수락한다. 혼자라면 관문이나 재도전 메뉴에서 바로 입장한다.
3. 다인 보스전에서 쓰러지면 생존 동료를 관전하고 ‘다음 파티원’으로 대상을 바꿀 수 있다. 보스 처치 또는 전멸 시 함께 야영지로 돌아간다. 어느 파티원이 마지막 타격을 넣든 입장 시 의뢰를 갖고 있던 참가자 전원이 보고할 수 있다. 도중 사망하거나 접속을 끊어도 인정된다. [관전과 복귀](BOSS_PROTOTYPE.md#파티-보스-관전)
4. 경비대장에게 보고해 100골드, 강화석 10개, 정제 강화석 1개, 전설 +0 **잠든 용의 검** 한 자루를 받는다. 재도전할 때는 이 검을 해제한다. 전장에서도 검 장착을 제한한다.
5. 현재 버전에서는 마을 대장장이에게 말을 걸고 **장비 강화**에서 보상 검을 선택하면 비용과 결과별 확률을 볼 수 있다. 잠든 용의 검은 각 세트에 한 부위로 계산한다. 강화의 파괴 판정은 기존 단계 하락과 같이 한 단계 내려간다.

## 플레이 검증 결과

| 상황 | macOS에서 확인한 결과 |
|---|---|
| 새 계정의 첫 도전 | A가 경비대장에게 의뢰를 받고 인벤토리에서 첫 보상 검을 장착했다. 사냥터에서 HUD 공격으로 적을 처치한 뒤 ‘능선의 위협’을 보고하고 ‘능선의 주인’을 수락했다. |
| 파티와 솔로의 동시 도전 | B가 초대를 한 번 거절하고 다시 수락했다. A·B는 같은 방, C는 별도 방에 들어갔다. 각 클라이언트에는 자기 방의 플레이어와 보스만 보였다. |
| 접속 종료 중 공동 처치 | B의 연결이 서버에서 해제된 뒤 A가 HUD 공격으로 파티 보스를 처치했다. B는 같은 계정으로 재접속해 의뢰를 보고할 수 있었다. C의 보스 체력은 84로 유지됐다. |
| 보고와 강화 | 승리한 A에게 경비대장이 100골드, 강화석 10개, 정제 강화석 1개와 검 1개를 지급했다. 재보고 시 보유량이 같았다. 인벤토리에서 +1로 강화한 뒤 앱을 껐다 켜자 같은 ID의 +1 검 한 자루, 137골드, 강화석 9개와 정제 강화석 1개가 남았다. |
| 재도전 | A가 용흔의 검을 착용하자 서버가 입장을 거절했다. 검을 해제한 뒤 마을에서 재도전했고, 전장 안에서 보낸 검 착용 요청도 거절됐다. |

첫 시나리오는 A의 게스트 생성부터 진행했다. B와 C의 선행 의뢰는 진행 API로 준비했다. [3인 플레이 관찰값과 재접속 결과](verification/boss-party/party-and-solo.json)

필드 선택은 두 macOS 클라이언트에서 Unity Input System의 가상 터치·마우스로 따로 확인했다. 640×480 화면에서 기사를 직접 누르고 떼자 초대 창이 열렸다. 초대·거절·재초대·수락 버튼에도 좌표 입력을 보내 두 클라이언트에 같은 2인 파티가 표시되는 것을 확인했다. [필드 선택 좌표·입력 프레임·버튼 기록](verification/boss-party/field-input.json)

별도 검증에서는 Unity 클라이언트 다섯 개로 4인 파티와 솔로 도전을 동시에 열었다. 아래 시나리오는 선행 의뢰와 비교용 방어구를 미리 준비하고, 창을 표시하지 않는 클라이언트에서 서버 요청과 HUD 버튼을 호출했다. 두 방에서 각각 HUD 공격으로 보스를 처치했다. [5인 동시 접속 관찰값과 계정별 결과](verification/boss-party/four-player-party.json)

| 상황 | 관찰 결과 |
|---|---|
| 정원과 독립 전투 | 4인 파티의 다섯 번째 초대를 서버가 거절했다. 다섯 번째 기사가 재접속해 별도 보스방을 열었고, 파티 승리 후에도 그 보스의 체력은 84였다. 이후 솔로 기사도 승리·보고했다. 파티 네 계정의 저장값과 승리 횟수는 그대로였다. |
| 사망자와 미수락자 | 관전 도입 전 검증에서 B는 보스를 한 번도 때리지 않고 사망했다. 마을에서 체력 112로 부활한 뒤 동료가 승리하자 보고할 수 있었다. 같은 방에 있던 미수락자 D도 마을로 돌아왔지만 의뢰와 보상은 받지 않았다. |
| 서로 다른 세트 장착 | 맹공 투구와 생명 방어구를 착용한 A가 보상 검을 장착했다. 맹공 2·생명 2·균형 1부위가 됐고, 체력은 132→144, 공격력은 14→33, 방어력은 6→8로 올랐다. |

## 검증 환경

macOS에서 게임 서버와 여러 Unity 클라이언트를 별도 프로세스로 실행했다. 검증용 SQLite와 루프백 포트를 사용했다. 검증 도구가 캐릭터 위치를 잡고 화면의 버튼 동작과 소유자 요청을 호출했다. 직접 터치감을 평가하는 Android·iOS 실기기 검증은 TODO-027에 남겨 둔다. 승리 연출은 마을 복귀와 결과 창을 사용한다.

HTTP·SQLite 회귀 테스트 15건이 통과했다. 동일한 처치·보고·강화 요청을 재전송해도 다시 적용되지 않았고, 기존 형식 계정의 완료 상태와 보유 장비도 유지됐다. 일반 방어구와 용흔의 검에 같은 파괴 판정을 강제했을 때 방어구는 사라졌고 검은 +5에서 +4, +6에서 +5로 내려갔다. [서버 테스트](../localServer/test_gameplay.py) · [서버 API와 실행 명령](../localServer/README.md)

## 같은 Mac에서 실행

아래 명령은 TODO-023 검증 당시의 빌드 조합이다. 통합 서버 실행기는 가장 높은 번호의 서버를 선택한다. 전용 보스가 적용된 버전을 플레이할 때는 최신 클라이언트와 서버를 함께 사용한다. [보스 프로토타입 실행 방법](BOSS_PROTOTYPE.md)

1. [통합 서버 실행기](../start-servers.command)를 실행한다. 이 버전의 전용 게임 서버는 [ServerBuild_5](../ServerBuild/ServerBuild_5/NetmarbleNeo)다.
2. 터미널을 하나 더 열고 저장소 루트에서 아래 명령으로 [TODO-023 클라이언트](../ClientBuild/TODO-023/NetmarbleNeo.app)를 실행한다. 같은 Mac의 로그인·게임 서버로 접속한다.

```sh
NEO_AUTH_URL=http://127.0.0.1:8080 NEO_GAME_ADDRESS=127.0.0.1 ./ClientBuild/TODO-023/NetmarbleNeo.app/Contents/MacOS/NetmarbleNeo
```

배포용 앱과 전용 서버를 함께 실행해 새 게스트의 ‘플레이 준비 완료’와 진행 정보 생성을 확인했다. 다중 클라이언트 전투 검증은 입력 도구가 있는 별도 빌드에서 실행했다. 이후 배포본에는 필드 선택 대상을 실제 접속한 플레이어로 제한하고, 의뢰가 보고 가능한 상태일 때 승리 창에 경비대장 안내를 표시하는 변경이 들어갔다. [배포본 해시와 접속 확인 기록](verification/boss-party/builds.json)
