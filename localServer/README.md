# 로컬 로그인 백엔드

Python 3.10 이상과 표준 라이브러리만 사용하는 HTTP JSON 서버다. Unity와 별도 프로세스로 실행하며 게스트 자동 인증, 아이디·비밀번호 회원가입·로그인과 계정별 게임 진행 저장을 제공한다. Unity 클라이언트는 기기에 저장된 게스트 자격 증명으로 계정을 생성하거나 복원하고, 발급된 액세스 토큰으로 NGO 게임 서버에 접속한다.

## 실행

터미널에서 아래 순서로 실행한다. 별도 패키지 설치는 필요 없다.

```sh
cd /Users/jinwoo/Documents/Github/NetmarbleNeo/localServer
python3 server.py serve
```

필드 6종의 경험치·골드·장비와 재료 드롭률, 수집 의뢰 아이템 드롭률, 보스 의뢰 보고 시 지급하는 재화는 Unity의 **몬스터 밸런스** 창에서 편집한다. 로그인 서버는 시작할 때 [보상표](monster_rewards.json)를 읽는다. Windows 서버를 갱신할 때는 `localServer`의 Python 파일과 JSON 파일을 함께 복사하고 기존 계정 DB는 그대로 사용한다. 수집 의뢰와 보스 의뢰는 수락할 때 정해진 조건·보상으로 끝까지 진행된다.

백엔드 API 테스트에 쓸 아이디·비밀번호 계정은 `python3 server.py create-user tester`로 만들 수 있다. 비밀번호를 두 번 입력한다. 기본 계정은 없다.

- 아이디: 영문·숫자·밑줄·하이픈 3~32자, 대소문자 구분.
- 비밀번호: 8~128자. 공백을 임의로 제거하지 않는다.
- 기본 주소: `http://127.0.0.1:8080`.
- 종료: 서버를 실행한 터미널에서 `Ctrl+C`.
- 저장: `localServer/data/auth.sqlite3`. 실행 위치와 관계없이 같은 기본 파일을 사용한다.

### 백엔드 전체 초기화

1. 게임 서버와 로그인 서버를 모두 종료한다. 에디터의 Server And Client 시나리오를 사용 중이면 플레이 모드를 중지한다.
2. `localServer` 폴더에서 macOS는 [reset-backend.command](reset-backend.command), Windows는 [reset-backend.cmd](reset-backend.cmd)를 더블클릭한다. 두 실행 파일 모두 위 서버와 동일하게 Python 3을 사용한다.
3. 표시된 DB 경로를 확인하고 대문자 `RESET`을 입력한다. 모든 계정·세션·게스트 토큰·장비·퀘스트·보스 도전·거래 기록이 함께 삭제된다. 완료 메시지가 나오면 서버를 다시 시작한다.

기본 대상은 `data/auth.sqlite3`이며 `LOCAL_SERVER_DB`를 설정했다면 그 경로를 사용한다. 서버를 `--db`로 실행했다면 같은 파일을 직접 지정한다. 예를 들어 Windows에서는 `py -3 server.py --db "D:\GameData\auth.sqlite3" reset-backend`, macOS에서는 `python3 server.py --db "/경로/auth.sqlite3" reset-backend`를 사용한다.

이미 로그인한 아이폰에서 서버 초기화 후 앱을 다시 열면, 서버가 키체인에 남아 있는 토큰을 거절하고 로그인 화면에 **새 게임 시작** 버튼이 나타난다. 버튼을 누르면 새로운 게스트로 레벨 1부터 시작한다. 서버 연결에 실패했다면 연결을 복구한 뒤 앱을 다시 열어 기존 게스트로 접속을 시도한다.

## API

| 메서드·경로 | 입력 | 결과 |
|---|---|---|
| `GET /health` | 없음 | 서버 응답 상태 |
| `POST /auth/register` | JSON `id`, `password` | 201, `{"user":{"id":"tester"}}` |
| `POST /auth/login` | JSON `id`, `password` | 사용자 ID, Bearer 토큰, 만료 시각 |
| `POST /auth/guest/create` | `guestToken`에 기기의 비공개 최초 생성 시드 | 기존/신규 게스트, 재로그인 자격, 단기 토큰 |
| `POST /auth/guest/resume` | `guestToken`에 서버가 발급한 재로그인 자격 | 같은 게스트의 새 단기 토큰 |
| `GET /auth/me` | `Authorization: Bearer <토큰>` | 로그인한 사용자 ID |
| `POST /auth/logout` | `Authorization: Bearer <토큰>` | 해당 토큰 무효화 |

회원가입·로그인 요청 본문 예시:

```json
{"id":"tester","password":"계정 생성 때 입력한 비밀번호"}
```

`Content-Type: application/json`으로 보낸다. 성공 응답 형식:

```json
{
  "accessToken": "발급된_불투명_토큰",
  "tokenType": "Bearer",
  "expiresAt": 1794650000,
  "user": {"id": "tester"}
}
```

위 만료 시각은 형식 예시다. 실제 값은 발급 시점부터 1시간 뒤의 Unix 초 단위 시각이다. 만료 후 다시 로그인한다. 재로그인은 새 토큰을 만들며 이전 토큰은 로그아웃 또는 만료까지 유효하다. 게임 서버는 `/auth/me`로 토큰을 확인한 뒤 접속을 승인한다.

오류 응답은 `{"error":"오류코드"}` 형식이다.

| HTTP | 의미 |
|---|---|
| 400 | 잘못된 JSON·필드·아이디/비밀번호 형식 |
| 401 | 로그인 실패 또는 유효하지 않은 토큰 |
| 409 | 회원가입 아이디 중복 (`ID_ALREADY_EXISTS`) |
| 413 | 요청 본문 크기 제한(4 KiB) 초과 |
| 415 | JSON이 아닌 요청 |
| 429 | 같은 IP에서 60초 동안 가입 또는 로그인 요청 10회 초과(각각 집계) |
| 503 | 저장소 사용 실패 |

## 로컬 네트워크와 설정

동일 PC의 에디터에서 접속할 때 기본 설정을 사용한다. 모바일 앱의 접속을 받는 서버에서는 다음처럼 모든 네트워크 인터페이스에서 수신한다.

```sh
python3 server.py serve --host 0.0.0.0 --port 8080
```

`0.0.0.0`은 서버가 연결을 받는 설정이며 클라이언트 접속 주소가 아니다. 개발 PC 방화벽과 공유기 환경에 따라 연결 허용이 필요할 수 있다. Unity 모바일 클라이언트의 HTTP 허용 설정·실기기 연결은 아직 검증하지 않았다.

환경변수 `LOCAL_SERVER_HOST`, `LOCAL_SERVER_PORT`, `LOCAL_SERVER_DB` 또는 명령행 인자로 설정을 바꿀 수 있다. DB 옵션은 하위 명령 앞에 둔다. 계정 생성과 실행에는 같은 DB 경로를 사용한다.

```sh
python3 server.py --db /absolute/path/auth.sqlite3 create-user tester
python3 server.py --db /absolute/path/auth.sqlite3 serve --port 8081
```

## 저장·보안과 현재 한계

- 비밀번호는 사용자별 무작위 salt와 PBKDF2-HMAC-SHA256 600,000회로 해시한다. 평문 비밀번호를 저장하지 않는다.
- 토큰은 무작위로 발급하고 DB에는 SHA-256 해시만 저장한다. 계정·세션은 서버 재시작 후에도 유지된다.
- DB 쿼리는 매개변수로 전달한다. 요청 본문·비밀번호·토큰은 로그로 출력하지 않는다.
- DB 파일은 생성 후 소유자 읽기·쓰기 권한으로 제한하며 `data/`는 버전 관리에서 제외한다.
- 회원가입·로그인 요청 제한은 단일 프로세스의 IP별 메모리 상태이며 서버 재시작 시 초기화된다.
- Python 기본 HTTP 서버를 이용한 **로컬 테스트용 구현**이다. 인터넷 공개 운영 전에는 HTTPS, 운영용 HTTP 서버, 배포·접근 제어·요청 제한·백업 구성을 별도로 검토해야 한다. 현재 HTTP 테스트에는 다른 서비스에서 사용하는 실제 비밀번호를 사용하지 않는다.

## 기존 아이디 계정으로 Unity에서 테스트

1. 위 명령으로 로그인 백엔드를 실행한다.
2. Unity에서 `ServerAndTwoClients` 시나리오를 실행한다.
3. 각 클라이언트에서 `Sign Up`을 선택하고 서로 다른 아이디로 가입한다.
4. 성공하면 DB 저장 → 자동 로그인 → Prototype 로드 → 게임 서버 인증 → Player 생성으로 이어진다.
5. 중복 아이디라면 다른 아이디를 입력하거나 `Back` → `Log In`으로 돌아간다.

가입은 성공했지만 자동 로그인이 실패하면 안내에 따라 `Submit`으로 로그인을 재시도한다. HTTP 응답을 받지 못한 경우 계정 생성 여부가 불명확하므로 먼저 로그인을 시도한다.

## 모바일 앱의 서버 접속

iOS·Android 앱은 `http://binaryRight.iptime.org:8080`으로 게스트 로그인 후 같은 호스트의 UDP 7777로 게임 서버에 접속한다. macOS에서 `start-lan.command`를 실행하면 기본 DB로 0.0.0.0:8080에서 로그인 요청을 받는다. [모바일 빌드와 집 서버 접속](../docs/LAN_IPHONE_SETUP.md)

## 게스트 인증

기기는 첫 네트워크 요청 전에 CSPRNG로 32바이트 시드를 만들어 보관한다. URL-safe Base64(패딩 제외) 또는 64자리 hex로 인코딩해 `/auth/guest/create`의 `guestToken`으로 보낸다. 서버가 계정 ID와 재로그인 토큰을 발급한다. 응답 유실 시 원래 시드로 create를 재시도하면 동일한 계정과 재로그인 자격이 반환된다. 계정·기본 진행·자격은 한 트랜잭션에 생성한다.

성공 응답에는 기존 로그인 필드와 `guestToken`, `guestExpiresAt`이 들어간다. 기기는 수신한 재로그인 자격의 보관을 마친 뒤 최초 생성 시드를 폐기한다. 다음 실행부터는 `/auth/guest/resume`에 재로그인 토큰을 보낸다. 재로그인 자격의 수명은 최초 발급 시점부터 180일, NGO 접속에 쓰는 단기 토큰은 1시간이다. 운영자가 `python3 server.py --db 경로 revoke-guest 계정ID`로 재로그인 자격과 현재 세션을 폐기할 수 있다. DB에는 시드·재로그인·세션 토큰의 검증용 해시를 보관한다.

저장된 재로그인 토큰으로 보낸 `/auth/guest/resume` 요청이 HTTP 401과 `GUEST_CREDENTIAL_INVALID`를 함께 반환할 때만 **새 게임 시작** 버튼이 나타난다. 플레이어가 누르면 기기는 새 생성 시드를 먼저 저장한 뒤 `/auth/guest/create`를 요청한다. 연결 실패, HTTP 408 또는 5xx 응답 시 앱은 2초 뒤 같은 자격으로 한 번 재시도한다. 생성 응답을 받기 전에 앱이 종료되더라도 다음 실행에서 같은 시드로 생성을 이어간다.

## 성장 체크포인트

게임 서버와 로그인 서버에 같은 `GAME_SERVER_KEY`를 설정한다. 게임 서버는 접속 시 검증한 계정 ID와 `X-Game-Server-Key` 헤더를 사용한다. 내부 키가 비어 있으면 내부 요청이 거절된다.

| 경로 | 기능 |
|---|---|
| `GET /progress/me` | 단기 Bearer 토큰 소유자의 전체 스냅샷 |
| `GET /internal/progress/{id}` | 게임 서버의 계정 상태 복원 |
| `POST /internal/progress/{id}/action` | 확정된 게임 행동을 한 번 반영하고 전체 스냅샷 반환 |
| `POST /internal/trade/commit` | 두 참가자가 확정한 장비·재료·골드를 함께 정산하고 양쪽 스냅샷을 반환 |
| `POST /internal/progress/{id}` | 구버전 `revision,objective,inventory,equipped,xpGain,rewardId` 요청 호환. 구형 장비의 소유·착용 표현만 갱신 |

행동 요청 예시다. `actionId`는 해당 행동이 확정될 때 한 번 만든다. 재전송 때 같은 값을 사용한다.

```json
{"actionId":"encounter-09","revision":3,"kind":"kill","target":"A1","npcId":""}
```

| kind | target | 판정 |
|---|---|---|
| kill | A1·A2·A3·A4·B1·B1G | 게임 서버가 처치 계정을 확정한 뒤 호출. XP, 골드, 드롭과 해당 계정의 수락된 처치 목표를 함께 반영 |
| accept / report | quest ID | `npcId` 필수. 게임 서버가 NPC와의 거리를 검사하며 백엔드는 NPC ID·레벨·선행·수량·상태를 재검사 |
| tutorial | 성공 행동 ID | 수락한 튜토리얼의 해당 목표만 전진. `open_inventory`, `move`, `attack_hit` 등 정의된 행동 ID 사용 |
| discoverBoss | ridge | 게임 서버가 도보 입구에서 캐릭터를 실제 보스 구역으로 옮긴 뒤 요청한다. 목표가 `boss` 또는 `complete`인 계정에 발견 상태를 한 번 저장한다. |
| equip / unequip | 소유한 장비의 instanceId | 계정·슬롯·현재 착용 상태 확인. 교체·스탯 갱신. 장착 성공 시 `equip` 튜토리얼도 같은 트랜잭션에 기록 |
| enhance | 소유한 장비의 instanceId | 대장장이에게 요청하는 수동 강화. `npcId="smith"`와 소유권·등급 상한·재료·골드를 확인하고 비용·추첨 결과·스탯을 함께 저장 |
| temper | 원정 준비에서 받은 검의 instanceId | 자동 진행의 ‘첫 담금질’. `npcId="smith"`, 미완료 상태로 수락한 의뢰, 지급 검의 +0 단계를 확인하고 일반 강화와 같은 비용을 적용 |
| sell | 미착용 사냥 장비의 instanceId | `npcId="warden"`. 서버가 마을·거리·생존 상태를 확인하고 DB가 장비 소유권·출처·착용 상태를 재확인한 뒤 매입 대금을 지급 |

409 `STALE_REVISION`이면 최신 스냅샷을 조회하고 아직 필요한 동작만 같은 ID로 재평가한다. 이미 성공한 요청을 재전송하면 최신 상태와 200을 반환한다. 같은 ID에 다른 동작을 붙이면 `ACTION_ID_REUSED`다. 이전 `POST /internal/progress/{id}`의 중복 보상 처리에는 기존 오류 `REWARD_ALREADY_APPLIED`를 유지한다.

처치 응답의 `lootResult.actionId`는 요청의 처치 ID다. `entries` 배열에 이번 처치로 지급한 골드, 장비, 재료를 담는다. 각 항목은 `type`(`gold`, `equipment`, `material`), `definitionId`, 한국어 `name`, 이번 지급량 `quantity`, `rarity`를 가진다. 골드의 ID는 `gold`이고 희귀도는 빈 문자열이다. 같은 처치 요청을 다시 보내면 최신 계정 상태에 당시 지급 내역을 붙여 반환한다. 진행 상태 조회와 지급 내역을 기록하기 전 버전의 처치에는 `lootResult`가 없다.

### 장비 판매와 플레이어 교환

경비대장의 매입가는 장비 한 개당 일반 30골드, 레어 100골드, 전설 300골드다. 필드 처치로 얻은 장비는 DB에 출처를 기록한다. 기존 DB에서는 처치 영수증과 의뢰 기록으로 식별되는 장비만 복원한다. 출처가 불분명한 기존 장비와 의뢰 지급품은 소유자가 계속 보관한다.

마을에서 기사 한 명을 선택해 거래를 신청한다. 각자 미착용 사냥 장비 최대 4개와 골드·강화석·정제 강화석의 수량을 제안할 수 있다. 양쪽이 같은 버전을 확정해야 게임 서버가 `tradeId`, `first`, `second`를 전송한다. 각 참가자에는 인증된 `userId`, 확인 당시 `revision`, `itemIds`, `gold`, `ore`, `rareOre`가 들어간다. 제안 수정은 양쪽의 확정을 해제하고, 확정 전에 마을을 떠나거나 접속을 끊으면 거래를 취소한다.

응답하지 않은 초대는 45초 후에 닫힌다. 수락 후 물품 수정이나 확정 없이 3분이 지나면 거래도 종료된다. 양쪽이 확정한 뒤에는 서버가 응답 유실 시에도 동일한 거래 ID와 제안으로 저장 결과를 확인한다.

백엔드는 `BEGIN IMMEDIATE` 안에서 양쪽 버전·소유권·잔액·수령 한도를 확인하고 두 계정의 자산, 버전, 거래 영수증을 함께 저장한다. 같은 ID와 같은 내용의 재전송은 최신 스냅샷을 반환한다. 같은 ID로 내용을 바꾸면 `TRADE_ID_CONFLICT`, 거래 준비 중 보유 상태가 바뀌면 `STALE_REVISION`을 반환한다. 회귀 검증은 저장소 루트에서 `python3 -B -m unittest localServer.test_gameplay localServer.test_trading`으로 실행한다. 테스트는 임시 SQLite와 로컬 HTTP 서버를 사용한다.

### 보스 도전 명단과 개별 보고

전용 게임 서버가 기존 내부 키로 아래 두 요청을 보낸다. `attemptId`는 도전마다 발급한 고유 ID다. 참가자의 사망이나 로그아웃 이후에도 로그인 서버가 최초 기록한 계정 명단을 사용한다.

| 요청 | JSON 본문 | 처리 |
|---|---|---|
| `POST /internal/boss/start` | `{"attemptId":"raid-01","members":["accountA","accountB"]}` | 1~4개 서로 다른 계정의 보스 입장 진행과 잠든 용의 검 미착용을 검사한다. 그때 ‘능선의 주인’ 의뢰를 수락해 진행 중인 계정만 처치 인정 명단에 기록한다. |
| `POST /internal/boss/clear` | `{"attemptId":"raid-01"}` | 해당 도전의 명단을 읽어 보스 처치 목표와 계정별 저장 버전을 한 트랜잭션으로 갱신한다. 재시도해도 목표와 버전은 한 번만 바뀐다. |

두 응답은 `{"attemptId":"raid-01","eligible":["accountA"],"cleared":false}` 형식이며 승리가 저장되면 `cleared`가 true다. 같은 도전 ID와 같은 명단의 시작 재전송은 원래 인정 명단을 돌려준다. 명단을 바꾸면 409 `ATTEMPT_ID_REUSED`다. 시작 전에 클리어 요청을 보내면 404 `UNKNOWN_ATTEMPT`다. 게임 서버는 실제 승리를 확정한 뒤 clear를 보내고 접속 중인 참가자의 스냅샷을 다시 읽는다. 오프라인 계정은 다음 접속 때 같은 결과를 받는다.

새 계정은 ‘관문 앞의 엄니’를 보고하고 20레벨에 도달하면 경비대장에게 ‘능선의 주인’(`ridge_boss`)을 수락할 수 있다. 두 조건 가운데 나중 조건을 달성한 거래에서 보스 입장 자격도 열린다. 목표를 달성한 사람이 직접 같은 NPC에게 보고하면 100골드, 강화석 10개, 정제 강화석 1개와 전설 +0 잠든 용의 검을 받는다. 보상 지급과 완료가 함께 저장된다. 이전 버전에서 이미 `boss` 또는 `complete`에 도달한 계정은 기존 레벨과 의뢰 이력으로 입장하고 수락할 수 있다. 이전에 수락한 ‘능선의 위협’을 보고하는 계정도 당시 계약대로 보스 자격을 얻는다.

### 장비 강화와 잠든 용의 검

마을 대장장이 반경 4m 안에서 강화할 수 있다. 게임 서버가 마을과 실제 거리를 확인하며 로그인 서버가 `npcId`를 재검사한다. 스냅샷의 `starterSwordInstanceId`는 ‘원정 준비’에서 지급한 일반 균형의 검을 가리킨다. 대장장이가 ‘첫 담금질’ 수락 때 강화석 1개를 주며, +0 → +1 시도에 강화석 1개와 10골드가 들고 성공률은 100%다. 해당 검을 수동으로 먼저 강화하면 의뢰를 수락할 때 완료된다. 튜토리얼 행동만 전송해서 강화 실적을 올리려는 요청에는 `ENHANCE_ACTION_REQUIRED`를 반환한다.

자동 강화에 다른 장비나 강화 단계를 지정하면 `STARTER_SWORD_REQUIRED`, 진행 중인 ‘첫 담금질’이 없으면 `TEMPER_QUEST_NOT_ACTIVE`를 반환한다. 완료 후 같은 행동 ID를 다시 보내면 저장한 결과를 돌려주고, 새 행동 ID로 다시 요청해도 재료와 골드가 보존된다. 이전 계정의 보상 기록에 개별 ID가 없을 때는 당시 ‘원정 준비’ 보상 정의와 소유 목록을 대조해 가장 먼저 생성된 일반 균형의 검을 연결한다. 이전 검 장착·사냥 의뢰를 이미 수락했거나 옛 지급 검이 없는 계정은 기존 동선을 이어간다.

장비별 `nextEnhance`는 다음 시도의 `ore,rareOre,gold` 비용과 `success,keep,downgrade,destroy` 정수 백분율을 반환한다. 상한에 도달하면 null이다. 각 시도에서 해당 비용을 소비한다. 일반 장비는 +5, 레어는 +6, 전설은 +7까지 올릴 수 있다. [11월 18일 장비·강화 설계표](../outputs/01a1e7d3-dac7-7681-a8af-d8ddcca9549d/장비_세트_강화_설계.xlsx)

강화 요청 응답에 `enhanceResult`를 넣으며 `actionId,instanceId,outcome,before,after`로 결과를 구분한다. `success`는 한 단계 상승, `keep`은 유지, `downgrade`는 한 단계 하락이다. `destroy`면 소유 목록에서 해당 장비가 사라지고 `after`는 -1이다. 응답 유실 뒤 같은 행동 ID로 재시도하면 당시 결과와 최신 계정 상태를 함께 받는다. 상한·재료 부족·골드 부족은 각각 409 `ENHANCEMENT_AT_CAP`, `INSUFFICIENT_MATERIALS`, `INSUFFICIENT_GOLD`를 반환하고 비용을 보존한다.

잠든 용의 검(`ridge_sword`)은 보스 의뢰 보상 전용이다. 검을 착용하면 맹공·생명·균형에 한 부위씩 기여하며, 예를 들어 맹공 투구와 생명 방어구를 함께 착용하면 두 세트의 2부위 효과가 적용된다. 각 장비의 `setBonuses`에 실제 착용 부위 수와 2·3부위 효과 수치를 담는다. 잠든 용의 검은 고단계 파괴 확률만큼 한 단계 하락 확률이 늘어난다. +5에서 +6은 하락 21%, +6에서 +7은 하락 27%이며 파괴 확률은 모두 0%다.

### 장비·캐릭터·기존 데이터 이행

스냅샷에는 `totalXp,level,levelXpThresholds,experience,objective,revision,gold,items,stats,quests,bossDiscovered`가 있다. `inventory,equipped`는 이전 클라이언트가 아는 종류만 담는 호환 필드다. 새 UI는 착용품을 포함한 전체 `items`와 개별 `instanceId`를 사용한다.

- `user_progress`는 XP를 1/100 단위 정수로, 골드는 정수로 저장한다. 레벨 1~20의 누적 XP 경계는 [성장 구현](progression.py)의 `THRESHOLDS`이며 최고 레벨 진입값은 2,040이다. 구버전 2,040 초과 XP도 보존한다. 최초 구버전의 레벨/퍼센트 행은 해당 시점의 10레벨 표로 누적 XP를 복원하고 현재 성장표로 표시한다.
- 구 `weapon_1~3`·`armor_1~3`는 검·방어구의 균형·맹공·생명 일반 +0으로 각각 이전한다. 계정·착용 관계·목표·보상 기록은 유지하고, 골드 신규 열의 초기값은 0이다. 이전 네 단계 `objective`는 보존하며 퀘스트별 수락·완료를 추측해 채우지 않는다.
- `item_instances`는 장비의 개별 ID·종류·등급·강화·착용 슬롯, `item_stacks`는 재료 수량을 보관한다. 상세의 `base,rarityBonus,enhanceBonus,setTwo,setThree` 및 `stats`는 같은 서버 계산에서 나온다. 세트 2부위와 3부위 증가분은 각각 한 번씩 적용된다. [장비 규칙](inventory.py)
- `game_actions`의 계정별 행동 ID와 `user_rewards`의 처치 ID는 장비·골드·퀘스트 진행과 함께 커밋된다. 기존 호환 요청은 새 장비 및 골드를 보존한다.
- `user_progress.boss_discovered`의 기본값은 0이다. 기존 계정도 보스 입구에 처음 도달해 입장을 확인하면 1이 되고, 이후 접속에서도 마을 재도전 자격을 유지한다.
- 첫 도보 입장이 성공하면 게임 서버는 발견 저장을 계정 대기열에 넣는다. 클라이언트 연결이 끊어져도 남은 저장을 같은 행동 ID로 재시도한다. 마을 입장은 DB에서 확정한 발견 상태를 기준으로 허용한다. 저장 응답은 소유자의 진행 화면을 갱신한다.

### 퀘스트 편집

[quests.json](quests.json)의 의뢰를 복제해 새 `id`, 목표별 `id`, 분류, NPC, 선행 ID, 레벨, 안내 문구, 대상·수량과 보상을 바꾼 뒤 서버를 다시 시작한다. `GAME_QUEST_FILE`로 별도 검증 파일을 지정할 수 있다. 잘못된 참조·중복 ID·순환 조건은 시작 시 어떤 정의인지 표시한다. 목표의 선택적 `label`은 클라이언트 표시명이며 `rewardLabel`에는 장비·재료·XP·골드의 실제 지급 내용이 담긴다. 수락한 계정에는 그 시점 정의가 함께 저장되어 편집 후에도 원래 약속한 목표·보상으로 완료된다. 신규 수락자는 편집된 정의를 사용한다.

`onAccept`와 `reward`는 수락 시점과 완료 시점의 XP·골드·장비·수량형 물품이다. 수집품은 보고 시점의 실제 수량을 다시 검사하고 전달과 보상을 원자적으로 처리한다. 튜토리얼은 `completion`을 `immediate` 또는 `report`로 설정한다. `allowExisting`이 true면 수락 이전에 기록한 해당 행동도 인정한다. 일반 장비 장착 목표는 현재 착용 상태를 사용한다. `equip_sword`는 실제 검 장착이 성공하면 기록하며, 수락 당시 착용한 검이나 앞서 기록된 검 장착도 인정한다.

선택적 `nextObjective`는 메인 의뢰 완료 시 구형 단일 목표 단계를 앞으로 갱신한다. 기존 계정의 더 먼 진행 단계는 보존한다.

기본 메인 의뢰 9개는 인벤토리 열기 → 대장장이에게 지급 검 +1 강화 → 검 장착 → A1 1마리 → A2 2마리 → A3 3마리 → A4 4마리 → 멧돼지 3마리 → 보스 처치 순서다. A2·A3·A4·멧돼지·보스 의뢰는 각각 3·5·10·15·20레벨부터 열린다. 보급품 전달은 별도로 수락하는 서브 의뢰다. 스냅샷의 의뢰별 `completion` 값은 `immediate`이면 목표 달성 즉시 완료, `report`이면 지정 NPC에게 보고해야 완료됨을 나타낸다.

수집 목표의 `dropFrom`은 재료를 주는 몬스터 ID, `dropChance`는 처치 한 번당 지급 확률(%)이다. ‘식지 않는 불씨’는 3레벨에 ‘능선의 위협’ 보고 후 대장장이에게 수락한다. A2의 잿불 심장석 2개를 전달하면 25골드와 강화석 1개를 받는다. ‘부러진 방책’은 15레벨에 ‘얼어붙은 고갯길’ 보고 후 경비대장에게 수락한다. B1 또는 B1G의 단단한 엄니 2개를 전달하면 60골드와 강화석 2개를 받는다. 두 재료 모두 의뢰를 수락한 계정이 2개를 모을 때까지 해당 몬스터를 처치할 때마다 50% 확률로 1개씩 얻는다.

퀘스트 스냅샷의 `minLevel`, `requires`와 계정의 `levelXpThresholds`로 HUD가 다음 의뢰의 조건을 표시한다. 처치 목표의 `alsoTargets`는 같은 목표 수량에 합산할 몬스터 ID 목록이다. 멧돼지 의뢰는 B1과 B1G 처치를 합산한다.

### 재현 검증

2026-11-24에 기존 진행 25개, 경비대장 매입 4개, 플레이어 교환 11개로 구성된 서버 테스트 40개가 모두 통과했다. 교환과 매입·강화·장착이 겹치는 경우, 두 구매자가 같은 재산을 요구하는 경우, 동일 거래의 6개 동시 요청, 영수증 저장 실패 등을 포함한 7개 테스트를 각각 25회 반복해 175회 모두 통과했다. 실패를 주입한 거래는 양쪽 계정과 영수증 전체가 원상복구됐고 같은 거래 ID로 재시도할 수 있었다.

같은 날 macOS에서 별도 Unity 프로세스 세 개(게임 서버 1개·클라이언트 2개)와 임시 로그인 서버를 띄워 교환했다. 테스트 씬에서 게임 버튼과 같은 소유자 RPC를 호출했다. A의 첫 확정 후 B가 골드 제안을 29에서 27로 바꾸자 양쪽 클라이언트에서 확정이 풀렸다. 두 사람이 변경된 제안을 확정한 뒤 두 클라이언트의 인벤토리와 SQLite를 대조했다.

| 계정 | 골드 | 강화석 | 정제 강화석 | 레어 +2 맹공의 검 | 계정 버전 |
|---|---|---|---|---|---|
| A | 100 → 114 | 4 → 2 | 0 → 1 | 보유 → 양도 | 0 → 1 |
| B | 80 → 66 | 0 → 2 | 3 → 2 | 수령, 같은 장비 ID·강화 단계 유지 | 0 → 1 |

DB에는 거래 영수증 한 건이 저장됐고, 받은 검의 매입가는 100골드였다. 별도의 응답 유실 검증에서는 서버가 저장한 직후 응답을 누락시켰다. 게임 서버의 C# 거래 코드는 같은 본문과 거래 ID를 재전송했고 재화는 한 번만 이동했다.

2026-11-23에 임시 SQLite와 루프백 HTTP로 서버 회귀 테스트 23개가 통과했다. 두 수집 의뢰에서 드롭 확률의 경계, 보유 상한, 보고 시 소모, 계정 격리, 재접속과 중복 처리를 확인했다. 같은 처치에는 한 번만 보상이 추가되고 재전송 응답에 처음 지급한 수량과 장비 등급이 복원됐다.

2026-11-22에 임시 SQLite와 루프백 HTTP를 사용하는 서버 회귀 테스트 21개가 통과했다. ‘첫 담금질’에서는 같은 종류의 다른 검·잘못된 NPC·수행 전송만으로는 진행되지 않았고, 동시에 들어온 같은 강화 요청은 10골드와 강화석 1개를 한 번만 소비했다. 수동 선강화, 재접속, 보상 ID가 없는 구버전 계정의 복원과 선행 의뢰 유지도 확인했다. 새 계정의 사냥 목표 13마리와 A1 보고 보상은 총 1,110 XP였다. 현재 구역에서 다음 수락 레벨까지 1·1·3·2·4마리를 추가로 잡아 20레벨에 도달했다.

2026-11-20에 임시 SQLite와 루프백 HTTP 서버로 아래 회귀 테스트 15개가 통과했다. 초기 레벨형 DB를 두 번 열어 완료 단계·기존 보상·착용 장비 보존 및 새 게스트 생성을 확인했다. 4인 명단에서 수락자 두 명과 시작 후 수락한 계정을 분리했고, 로그인 서버 재시작 후 동일한 승리 요청을 세 번 동시에 보내도 대상자별 저장 버전은 한 번씩 증가했다. 두 계정의 독립 보고와 보상 재전송, 종결 검의 혼합·동일 세트, 고단계 파괴 판정에서 일반 장비 소실과 종결 검 하락, 비용 부족·상한·응답 재전송을 확인했다. 착용한 보상 검에 같은 강화 확인 요청을 동시에 보내도 강화 단계와 비용이 한 번씩 적용됐고, 재인증 뒤 공격력 증가가 복원됐다. HTTP 테스트에서는 게임 서버 내부 키로 시작·처치를 요청하고 일반 계정으로 보고 가능 상태를 조회했다.

저장소 루트에서 `python3 -m unittest -v localServer.test_gameplay`를 실행한다. 테스트마다 임시 SQLite DB를 생성하며 HTTP 검증은 127.0.0.1의 임시 포트에만 바인딩한다. 2026-11-18 Python 3.13.2에서 게스트 생성 재시도와 재인증, 기존 데이터 이전, 데이터 편집·동시 전달, 실제 HTTP 인증·보상·저장 버전 충돌, 장착·해제와 최종 스탯을 검증했다. JSON 변경 테스트는 처치 대상 A1→B1, 필요 수량 2→3, 보고처 경비대장→대장장이를 함께 바꿔 신규 계정으로 완료한다. 기존 수락 계정은 변경 전의 진행도와 조건으로 끝낸다. 별도 튜토리얼 테스트는 수락 전 방문·기착용 장비 인정 여부, 사용 성공과 적중 성공의 구분을 확인한다.
